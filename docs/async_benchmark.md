## 4. 核心工程结论与量化归因

### 1. 实际物理并发瓶颈公式
$$\text{实际物理并发} = \min(\text{协程并发限制 (Semaphore / Concurrency)}, \text{底层物理连接池 (max\_connections)})$$
- **量化归因**：在组合 1 中，即便协程并发设为 100，但由于底层物理连接池仅有 10 个 TCP 套接字，导致 90 个协程在连接池门外产生严重的排队饥饿，引发 P99 恶化到 9 秒以上（长尾排队）；
- **生产法则**：应用层的协程信号量与底层 HTTP 客户端连接池必须保持 **1:1 匹配或连接池略大于并发**（如连接池 50 + 并发 50），避免无谓的连接池排队与超时崩溃（`httpx.PoolTimeout`）。

### 2. 瓶颈定位
- 异步 I/O 系统的瓶颈**从不在本地单线程的 CPU**，而在**网络 RTT（往返时延）**与**下游服务商的物理连接数 / 限流配额**；
- 盲目增大应用层并发只会导致内存堆积和长尾延迟，唯有配合“有界队列背压”才能使系统在高负载下保持线性稳定。

### 3. 大模型（LLM）API 限流选型思考
- **终极选型**：坚定选择 **`AsyncTokenBucket`（令牌桶）**。
- **原因**：
  1. **支持瞬时突发（Burstability）**：大模型智能体经常面临瞬间派生（如一个复杂任务瞬间派生 3 个工具调用），令牌桶平时积攒的容量支持毫秒级放行，保证交互极速响应；
  2. **严格长期保底**：注水速率 `rate` 从数学上卡死每分钟调用量绝不超过服务商 RPM（每分钟请求数）配额，杜绝 429 报错；
  3. **惰性计算（Lazy Evaluation）**：基于 `time.monotonic()` 按时间差推算，零后台空转线程，零 CPU 资源浪费。

## 5. 面试高频 5 题终极解答（通关自测）

### Q1: `asyncio.Semaphore(100)` 和 `httpx.Limits(max_connections=10)` 同时设置，实际并发是多少？为什么？
> **答**：实际物理并发是 **10**。  
> 信号量只是应用层协程允许同时飞行的门票（100 个），但每个协程真正向网络发包时，必须向 `httpx` 底层连接池借用物理 TCP Socket。因为只有 10 根物理管道，剩下的 90 个协程只能在连接池队列中挂起等待，系统真实并发被木桶最短板（10）卡死。

### Q2: `asyncio.gather` 里有一个任务抛异常，其余任务会怎样？`TaskGroup` 有什么不同？
> **答**：
> - `asyncio.gather`（默认 `return_exceptions=False`）：只要有 1 个任务抛异常，`gather` 就会立刻向外抛出该异常，**但其余仍在运行的任务不会被自动取消，继续在后台盲目运行，沦为孤儿/僵尸任务**；
> - `asyncio.TaskGroup`（Python 3.11+ 结构化并发）：其中任意一个任务崩溃，`TaskGroup` 会**自动把组内其余所有活跃任务全部 `cancel()`**，确保不会有任何后台任务遗留泄漏，实现真正的结构化生命周期闭环。

### Q3: `except Exception` 能拦住 `asyncio.CancelledError` 吗？为什么这个设计是对的？
> **答**：
> - **拦不住**。从 Python 3.8 起，`CancelledError` 继承自 `BaseException`，而不是 `Exception`。
> - **为什么是对的**：`CancelledError` 是操作系统的控制流中断指令（如外部超时 `wait_for` 或用户按停止），不是业务语法错误。如果 `except Exception` 能拦住它，就会导致取消信号被日常业务的 `try...except Exception` 生吞，使得超时控制失效、任务变成关不掉的后台僵尸。

### Q4: 1000 个并发 SSE（Server-Sent Events）长连接，每个连接在服务端占多少内存？怎么估算总量？
> **答**：
> - 单个长连接在服务端的物理内存主要包含：**TCP 接收/发送缓冲区（约 4KB~8KB）、Python 协程帧对象（约 2KB~4KB）、FastAPI/ASGI Request 上下文对象（约 10KB~20KB）**，单连接物理常驻内存约为 **20KB ~ 40KB**；
> - 估算总量：1000 个并发长连接通常占用 **20MB ~ 40MB** 内存。由于单线程 `asyncio` 没有线程栈（1MB/线程）的开销，因此 1000 个长连接对单台服务器非常轻量。

### Q5: 令牌桶和滑动窗口限流分别适合什么场景？给 LLM API 限流你选哪个？
> **答**：
> - **令牌桶**：允许突发（Burst），产水速率平稳，适合“平时低频、偶发集中一波”的场景（如 LLM Agent 工具调用）；
> - **滑动窗口**：严格限制任意滑动时间窗口（如任意过去的 60 秒内）不可越界，适合强一致性金融扣费与全局账单配额；
> - **选型**：给客户端调用 LLM API 限流选**令牌桶**，既能兼顾 Agent 的突发推理体验，又能在数学上保证长期调用不超频被封号。
